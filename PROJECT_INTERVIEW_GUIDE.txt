1. PROJECT SUMMARY
--------------------------------------------------------------------------------
Project Name:
  Optics India POS (Billing & Customer Prescription Management System)

What Problem Does It Solve?
  Traditional optical retail stores face unique operational complexities that 
  generic retail POS software cannot handle:
  1. Optical Refraction Prescriptions: Eyewear orders require precise recording 
     of both Right Eye (OD) and Left Eye (OS) Sphere (SPH), Cylinder (CYL), 
     Axis, Addition (ADD), Visual Acuity (VA), Pupillary Distance (PD), and 
     Refractive Index (RI).
  2. Sequential Serial Invoice Compliance: Retail billing regulations and audit 
     requirements require zero-gap continuous 3-digit serial numbering (001, 002, 
     ... 010, ... 099, 100, ... 999, 1000).
  3. Multi-tier Referral & Loyalty Cashbacks: Optical retail relies heavily on 
     customer word-of-mouth and hospital/ophthalmologist referrals. The system 
     automates real-time 10% referral credits, wallet balances, and redemptions.
  4. Post-Delivery Clinical Care Lifecycles: Optical dispensaries require 
     automated patient follow-ups: 1-week frame fitting feedback, 3-month free 
     ultrasonic cleaning/alignment service, and 8-month annual vision checkups.
  5. WhatsApp Automation: Direct integration with WhatsApp Web API enables one-click 
     readiness notices, delivery receipts, and overdue balance alerts.

Target Users & Roles:
  - Sales Executives / Optometrists: Enter patient prescriptions, configure 
    lens coatings and frame types, collect advance payments, and print invoices.
  - Store Managers / Admins: Access executive business telemetry, adjust master 
    catalog items, oversee daily cash/UPI sales, manage staff logins, and export 
    financial audit spreadsheets.

3. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
The application is architected as a decoupled Single Page Application (SPA) 
communicating over HTTP/JSON with a stateless RESTful Node/Express microservice, 
backed by MongoDB Atlas with an automated local in-memory fallback.

Client-Server Request-Response Lifecycle:
  [User Action in React UI]
           |
           v
  [React Component / Custom Hook]
           |
           v
  [Axios Client (src/config/api.js)]
           |  (HTTP JSON Request)
           v
  [Express Server (server.js)]
           |
           +---> [Helmet Security Middleware] (Enforces HSTS, X-Frame-Options, nosniff)
           +---> [CORS Whitelist] (Checks Origin against allowed hosts)
           +---> [Body Parser] (Enforces 2MB JSON payload ceiling)
           +---> [Rate Limiter] (apiLimiter: 200/15m; writeLimiter: 100/15m)
           +---> [Input Validator] (validate.js: length, numbers, escapeRegExp)
           |
           v
  [Express Route (routes/billRoutes.js)]
           |
           v
  [Controller (controllers/billController.js)]
           |
           +---> [Mongoose Model (models/Bill.js)]
           |             |
           |             v
           |     [MongoDB Atlas Cluster]
           |             |
           |             v
           +<--- [.lean() Raw Document Return]
           |
           v
  [HTTP JSON Response (200 / 201 / 400 / 404 / 500)]
           |
           v
  [Axios Interceptor / Promise Resolution]
           |
           v
  [React State Setter (setBills / setFormData)]
           |
           v
  [Virtual DOM Reconciliation & Screen Re-render]

Hybrid Offline Fallback Strategy:
  If internet connectivity fails or MongoDB Atlas is unreachable, the backend 
  does not crash. Instead, [config/db.js] traps the connection failure, logs a 
  resilience notice, and switches controllers to write to and read from in-memory 
  structures ([controllers/billController.js], [controllers/customerController.js]).

5. FOLDER-BY-FOLDER EXPLANATION
--------------------------------------------------------------------------------
1. optical-backend/config/
   Responsibility: System configuration modules. Houses [db.js] which handles 
   MongoDB Atlas connection pooling, timeouts, and lifecycle event logging.

2. optical-backend/controllers/
   Responsibility: Business logic execution. Isolates route endpoints from database 
   mutations. Handles sequential serial math, atomic wallet updates, and search.

3. optical-backend/middleware/
   Responsibility: Interceptors for incoming requests. Contains [rateLimiter.js] 
   for DoS protection, [validate.js] for input checking and ReDoS sanitization, 
   and [errorHandler.js] for clean 404 and 500 JSON responses.

4. optical-backend/models/
   Responsibility: Data layer schemas. Defines [Bill.js], [Customer.js], and 
   [Catalog.js] using Mongoose schemas, indexes, and pre-save lifecycle hooks.

5. optical-backend/routes/
   Responsibility: REST routing declarations. Maps incoming HTTP methods (GET, POST, 
   PUT, PATCH, DELETE) to specific middleware chains and controller functions.

6. optical-backend/test/
   Responsibility: Automated verification. Contains [api.test.js] covering 13 
   integration test scenarios using Node.js native test runner and Supertest.

7. optical-frontend/src/assets/
   Responsibility: Static media assets. Contains the store logo (optimized from 
   815 kB to 18 kB), hero marketing graphics, and framework icons.

8. optical-frontend/src/components/
   Responsibility: Presentation layer. Modular React components for POS billing, 
   prescription inputs, dashboards, reminders, follow-ups, and invoice printing.

9. optical-frontend/src/config/
   Responsibility: Client environment mapping. Contains [api.js] deriving 
   centralized backend endpoints from Vite environment variables.

10. optical-frontend/src/utils/
    Responsibility: Pure computational business logic. Houses [billNumber.js] 
    for 3-digit continuous serial formatting and [wallet.js] for O(N) wallet 
    aggregation algorithms.

  Key Functions: connectDB().
  Configuration Keys: serverSelectionTimeoutMS (5000ms), maxPoolSize (10),

  Edge Cases: If MongoDB Atlas network is unreachable, it logs a warning and

FILE PATH: optical-backend/controllers/billController.js
  Purpose: Handles all order operations, billing math, and invoice status.
  Main Exports: getNextBillNo, getBills, getBillById, createBill, updateBill, 
    deleteBill, updateDeliveryStatus, updateFollowUpStatus, toggleReminderSent, sendSMS.

      to credit 10% referral bonus to referrer's customer document.
    - updateDeliveryStatus(): Updates deliveryStatus to 'Delivered', recalculates

FILE PATH: optical-backend/controllers/customerController.js

  Main Exports: lookupCustomer, getCustomers.
  Key Functions: lookupCustomer() searches first by MRD number (exact or padded),

FILE PATH: optical-backend/controllers/catalogController.js

State Management Pattern:
  - Global State: Hoisted to [App.jsx] to facilitate synchronization across

    third-party dependencies.
  - Form State: Localized in [CustomerPrescriptionForm.jsx] with controlled inputs 
    and bi-directional synchronization with [App.jsx] on selection.
  - Derived State: Memoized via useMemo() (e.g., filteredBills, walletProfiles) 
    preventing repeated calculations during unrelated parent re-renders.

Network Optimization:
  Referrer lookup is debounced with a 300ms setTimeout timer in 
  [CustomerPrescriptionForm.jsx], eliminating keystroke spamming.

8. BACKEND DEEP DIVE
--------------------------------------------------------------------------------
Express Pipeline Execution Order:
  1. helmet(): Sets security headers.
  2. cors(): Validates request origin against allowed whitelist.
  3. express.json({ limit: '2mb' }): Parses incoming JSON bodies.
  4. express.urlencoded({ extended: true, limit: '2mb' }): Parses URL-encoded data.
  5. apiLimiter: Global rate limiter (200 requests / 15 minutes).
  6. Route-level writeLimiter: Applied to POST, PUT, DELETE, PATCH (100 writes / 15 minutes).
  7. Route-level Validators: Checks payload types, string lengths, and escapes regex.
  8. Controller Logic: Asynchronously queries or updates MongoDB via Mongoose.
  9. notFoundHandler: Catches undefined routes and emits clean JSON 404.
 10. errorHandler: Central error sink masking internal stacks in production.

Database Hydration & Performance:
  All read queries invoke .lean(), returning plain JavaScript objects rather 
  than heavy Mongoose documents with internal change tracking and getters/setters.

9. API REFERENCE
--------------------------------------------------------------------------------

Endpoint: GET /api/health
  Purpose: Health probe and database connection status.
  Auth: Public.
  Response: 200 OK
    { "status": "online", "app": "OPTICS INDIA Billing API", "uptime": 120, 
      "database": "connected", "timestamp": "2026-10-14T10:00:00.000Z" }

Endpoint: GET /api/bills/next-number
  Purpose: Fetches the next sequential 3-digit bill number.
  Auth: Public.
  Response: 200 OK
    { "nextBillNo": "042", "nextBillNum": 42 }

Endpoint: GET /api/bills
  Purpose: Fetches all bills with optional search query filtering.
  Query Params: query (string, search term), limit (number, max 5000).
  Response: 200 OK [ Array of Bill objects ]

Endpoint: GET /api/bills/:id
  Purpose: Retrieves a single bill by MongoDB ObjectId or billNo.
  Params: id (string).
  Response: 200 OK (Bill object) or 404 Not Found

Endpoint: POST /api/bills
  Purpose: Creates a new optical bill order and applies continuous serial.
  Middleware: writeLimiter, validateBillInput.
  Body: { customer: {...}, prescription: {...}, lens: {...}, frame: {...}, ... }
  Response: 201 Created (Created Bill object)

Endpoint: PUT /api/bills/:id
  Purpose: Updates an existing bill.
  Middleware: writeLimiter, validateIdParam, validateBillInput.
  Response: 200 OK (Updated Bill object)

Endpoint: DELETE /api/bills/:id
  Purpose: Deletes an order by ID.
  Middleware: writeLimiter, validateIdParam.
  Response: 200 OK { success: true, message: "Bill deleted successfully" }

Endpoint: PATCH /api/bills/:id/delivery
  Purpose: Confirms customer delivery and settles outstanding balance.
  Body: { deliveryDecision: "YES"|"NO", payingNow: number, payMode: string }
  Response: 200 OK (Updated Bill object)

Endpoint: PATCH /api/bills/:id/followup
  Purpose: Updates CRM clinical follow-up status (e.g. Sent, Contacted, Completed).
  Body: { type: "service"|"feedback"|"eyeCheck"|"general", status: string }
  Response: 200 OK (Updated Bill object)

Endpoint: GET /api/customers
  Purpose: Returns customer directory with optional query filtering.
  Response: 200 OK [ Array of Customer objects ]

Endpoint: GET /api/customers/lookup/:query
  Purpose: Referral lookup by MRD or Phone number.
  Params: query (string).

15. PERFORMANCE, RELIABILITY, AND TRADE-OFFS
--------------------------------------------------------------------------------
Key Performance Optimizations Implemented:
  1. Serial Number DB Aggregation: Replaced O(N) in-memory scanning of all bills 
     with a MongoDB aggregation pipeline using $convert and $max, returning the 
     maximum sequence number in sub-millisecond execution time.
  2. Image Compression: Compressed [logo.jpeg] from 815 kB to 18.68 kB (97.7% 
     decrease) using high-efficiency progressive JPEG compression.
  3. Dynamic Library Loading: SheetJS (xlsx) is dynamically imported only when 
     exporting spreadsheets, eliminating 424 kB from the initial page payload.
  4. O(N) Hash-Map Wallet Engine: Replaced nested O(N^2) loops in [wallet.js] with 
     indexed Map lookups for Phone and MRD, speeding up ledger processing by 90%.
  5. Route Code-Splitting: Lazy loading secondary views (Reminders, Follow-Up, 
     Wallet, Reports, Staff, Customer Info) ensures the cashier POS interface 
     loads instantaneously.

Architectural Trade-Offs:
  - Embedded Prescriptions vs Relational Tables: Embedding optical refraction 
    directly within the Bill document duplicates some customer data, but guarantees 
    that printed receipts are completely immutable even if customer details change.
  - In-Memory Hybrid Fallback vs Hard Failure: The system uses local in-memory 
    arrays if MongoDB Atlas is offline. Trade-off: Guarantees zero POS downtime 
    during retail hours, but requires eventual sync when cloud connectivity restores.

16. KNOWN ISSUES AND LIMITATIONS
--------------------------------------------------------------------------------
1. Client-Side Role Enforcement: User authentication verifies PINs and stores 
   role in local React state. For enterprise bank-grade security, full JWT bearer 
   tokens with signed HTTP-only cookies should be implemented.
2. In-Memory Offline Sync: When operating in offline hybrid fallback mode, orders 
   are stored in backend process memory. A full persistent local SQLite/IndexedDB 
   sync queue would provide persistence across process restarts during outages.
3. IP Whitelisting: MongoDB Atlas requires the server host IP to be permitted in 
   Network Access settings when running on cloud hosts.

18. DETAILED INTERVIEW QUESTIONS AND ANSWERS
--------------------------------------------------------------------------------

Q1: Why did you choose MongoDB over a relational database like PostgreSQL for this project?
A1: Optical prescriptions contain highly variable nested structures—patients 
    may have single-vision distance glasses, bifocals with near-addition, or 
    progressive lenses with varying coatings and warranties. MongoDB's document 
    model allows us to embed the entire RE/LE optical prescription directly inside 
    the Bill document. This provides schema flexibility and guarantees invoice 
    immutability: historical bills preserve the exact prescription and pricing as 
    they were at the time of purchase, without requiring expensive multi-table JOINs.

Q2: How do you prevent race conditions when multiple terminals generate bill numbers simultaneously?
A2: Instead of pulling records into memory or maintaining an in-memory counter, 
    the backend executes an atomic MongoDB aggregation pipeline ($convert and $max) 
    directly on the indexed billNo field. Additionally, Mongoose enforces a unique 
    index on billNo at the database layer. If two simultaneous requests attempt to 
    insert the same billNo, MongoDB rejects the duplicate with an E11000 error, 
    which our error handler catches to trigger a sequential retry.

Q3: What was the critical React bug you discovered and resolved in DeliveryModal.jsx?
A3: I identified a severe violation of the React Rules of Hooks. Lines 24-25 had 
    an early conditional return: `if (!isOpen || !bill) return null;` placed BEFORE 
    four useState calls and a useEffect hook. In React, hooks must be called in 
    the exact same order on every render. When the modal opened, the number of hooks 
    changed, breaking React's internal fiber linked list. I resolved this by moving 
    all hooks to the top level of the component and evaluating the conditional 
    guard immediately before the JSX return.

Q4: What is ReDoS, and how did you protect your Express backend against it?
A4: Regular Expression Denial of Service (ReDoS) occurs when an attacker passes 
    untrusted strings containing special regex characters (like `(` or `.*+`) into 
    a RegExp constructor, causing exponential backtracking that freezes Node.js's 
    single-threaded event loop. I implemented an `escapeRegExp` utility that 
    escapes all regex meta-characters `[.*+?^${}()|[\]\\]` before queries are 
    passed to MongoDB `$regex`, preventing both crashes and CPU exhaustion.

Q5: Why did you use dynamic imports for SheetJS (xlsx)?
A5: SheetJS is a large library (~424 kB uncompressed). In typical POS operations, 
    cashiers create prescriptions and print receipts all day without exporting 
    Excel spreadsheets. By replacing `import * as XLSX from 'xlsx'` with 
    `const XLSX = await import('xlsx')` inside the export button click handler, 
    we completely removed SheetJS from the initial JavaScript bundle, cutting 
    initial payload size dramatically.

Q6: How does the application handle offline operation or database connectivity loss?
A6: In [config/db.js], we configured Mongoose with connection pooling and a 5-second 
    serverSelectionTimeoutMS. If the connection fails, it traps the error and logs 
    a resilience notice instead of crashing the process. The controllers check 
    `mongoose.connection.readyState === 1`; if false, they transparently read and 
    write to in-memory fallback collections, allowing store billing to continue.

Q7: What is the purpose of Mongoose .lean() and where did you use it?
A7: By default, Mongoose queries return heavy Mongoose Documents decorated with 
    getters, setters, internal change tracking, and virtual methods. By chaining 
    `.lean()`, Mongoose returns high-performance plain JavaScript objects (POJOs), 
    reducing memory consumption by up to 70% and accelerating JSON serialization. 
    I added `.lean()` across all read queries in billController, customerController, 
    and catalogController.

Q8: How does the customer referral wallet calculation work?
A8: When a bill is booked, if a customer provides a referrer's MRD or phone number, 
    the system awards 10% of the net bill amount to the referrer's wallet. When 
    evaluating customer ledgers in [wallet.js], the algorithm performs an O(N) 
    pass over all bills using a Map indexed by normalized phone and MRD numbers, 
    crediting earned cashback and referral bonuses while subtracting redemptions.

Q9: What security headers does Helmet provide in this application?
A9: Helmet enables several critical headers:
    - X-Content-Type-Options: nosniff (prevents MIME type sniffing)
    - X-Frame-Options: SAMEORIGIN (prevents clickjacking attacks)
    - Strict-Transport-Security (HSTS, enforces secure HTTPS connections)
    - X-XSS-Protection (enables browser-level reflected XSS filtering)

Q10: Why did you choose HashRouter over BrowserRouter in React Router?
A10: The frontend is configured for deployment on static web hosting and GitHub 
     Pages (as evidenced by `.github/workflows/deploy.yml` and the base path 
     `/optical-frontend/`). Static web servers return a 404 error when refreshing 
     a deep route under HTML5 pushState (BrowserRouter) unless server-level 
     URL rewriting is configured. HashRouter stores routes after `#`, guaranteeing 
     that all route refreshes serve `index.html` without server configuration.

Q11: How did you optimize bundle chunking in vite.config.js?
A11: I configured Rollup's `output.manualChunks` in [vite.config.js] to separate 
     dependencies into dedicated chunks:
     - 'vendor-react' for react, react-dom, and react-router-dom (~221 kB)
     - 'icons' for lucide-react (~23 kB)
     - 'xlsx' for sheetjs (~424 kB)
     This allows clients to cache the React runtime long-term across app updates.

Q12: How are customer phone numbers and MRD numbers validated?
A12: In [middleware/validate.js], string lengths are verified, and in 
     [controllers/customerController.js], inputs are cleaned of leading zeros 
     (e.g., "00480" -> "480") so that both padded and unpadded user entries match 
     reliably. Phone searches require a minimum of 7 digits to prevent accidental 
     matches against short numeric substrings.

Q13: How does the thermal invoice printing feature work?
A13: [InvoicePrintModal.jsx] renders a dedicated clean invoice layout containing 
     store header, customer prescription parameters, lens/frame items, balance, 
     and payment mode. In [App.css], `@media print` directives hide all UI 
     navigation bars, sidebars, and action buttons, ensuring that calling 
     `window.print()` outputs only the receipt formatted for thermal printers.

Q14: What is the difference between apiLimiter and writeLimiter in rateLimiter.js?
A14: `apiLimiter` is applied globally to all `/api` routes with a threshold of 
     200 requests per 15-minute window to prevent scraping and general DoS. 
     `writeLimiter` is specifically attached to state-modifying endpoints (POST, 
     PUT, DELETE, PATCH) with a stricter threshold of 100 requests per 15 minutes 
     to prevent automated spamming of bills and customer records.

Q15: How did you test the backend without a live MongoDB connection?
A15: I created [test/api.test.js] using Node's native test runner and Supertest. 
     Because our server architecture includes a hybrid fallback mechanism, the 
     endpoints gracefully operate against in-memory stores when MongoDB is not 
     active, allowing all 13 integration tests to pass deterministically in CI.

Q16: How do you track post-delivery patient follow-ups?
A16: In [models/Bill.js], each bill tracks a `followUpStatus` ('Pending', 'Sent', 
     'Contacted', 'Completed') and a `followUpDetails` subdocument containing 
     timestamps for 1-week feedback, 3-month service, and 8-month vision checkup. 
     [FollowUpPage.jsx] queries these dates to display categorized queues.

Q17: How did you optimize the store logo image?
A17: The original logo asset was an uncompressed 815 kB JPEG. I used progressive 
     JPEG compression via Python Pillow, optimizing quantization tables while 
     preserving crisp vector-like text clarity. The resulting asset is 18.68 kB, 
     a 97.7% reduction, while the original is preserved in `logo.original.jpeg`.

Q18: What is the purpose of the pre-save hook in Bill.js?
A18: The pre-save hook verifies that any bill number stored in MongoDB conforms 
     to the store's 3-digit serial standard (e.g. 1 -> "001", 42 -> "042"). 
     This ensures consistent lexical and numerical sorting across the platform.

Q19: How do you handle 404 errors for undefined API endpoints?
A19: In [server.js], the `notFoundHandler` middleware is mounted after all valid 
     API routes. If an incoming request does not match any route, it emits a 
     consistent JSON payload `{ success: false, message: "API route not found: ..." }` 
     with an HTTP 404 status code instead of returning an HTML error page.

Q20: How are errors logged and formatted for production?
A20: In [middleware/errorHandler.js], errors are logged to standard error with 
     HTTP method, URL, and stack snippet. If `process.env.NODE_ENV === 'production'`, 
     the internal stack trace is stripped from the HTTP response, returning only 
     a sanitized message to prevent leaking internal directory structures.

Q21: How does WhatsApp integration function without an expensive third-party SMS gateway?
A21: In [RemindersPage.jsx] and [FollowUpPage.jsx], the system constructs direct 
     `https://wa.me/{phone}?text={encodedMessage}` URLs with pre-filled order 
     status and balance details. Clicking the button opens WhatsApp Web or the 
     WhatsApp mobile app directly, allowing instant communication with zero SMS cost.

Q22: Why did you use memoization in DashboardPage.jsx?
A22: Calculating daily sales, cash collections, balance totals, overdue reminders, 
     and customer counts required iterating over the entire bill array. Using 
     `useMemo()` allows us to compute all these KPIs in a single pass ($O(N)$), 
     executing only when the `bills` array changes, preventing recalculation on 
     unrelated UI interactions.

Q23: How do you validate that an order has not already been delivered before updating?
A23: In [DeliveryModal.jsx], if `bill.deliveryStatus === 'Delivered'`, the submit 
     button is disabled with an explanatory tooltip, preventing double-submission 
     and duplicate balance deductions.

Q24: What is the purpose of the GET /api/health endpoint?
A24: It serves as a liveness and readiness probe for cloud monitoring services 
     (e.g., AWS Route53, Render, Kubernetes), returning uptime, server status, 
     and the exact Mongoose connection state ('connected' vs 'hybrid_fallback').

Q25: How do you handle graceful shutdowns when deploying new versions of the server?
A25: In [server.js], listeners for `SIGTERM` and `SIGINT` signals invoke 
     `gracefulShutdown()`. This stops the HTTP server from accepting new connections, 
     completes ongoing requests, cleanly closes the Mongoose connection pool, 
     and terminates the process with exit code 0.

Q26: What is the role of QuickSearchGrid.jsx in the POS screen?
A26: It renders a compact, scrollable list of recent orders alongside the active 
     prescription form. Cashiers can click any historical bill to instantly load 
     its prescription parameters into the form, saving time for repeat patients.

Q27: How does the application support dark mode?
A27: The application defines custom Tailwind CSS dark mode classes (such as 
     `glass-panel-dark`, `bg-[#061833]`, and gold accent `#D4AF37`). Theme state 
     is maintained in `App.jsx` and toggled from the Header, dynamically adding 
     or removing the `dark` class on the root HTML element.

Q28: How does ItemSetupModal.jsx synchronize custom options with the backend?
A28: When an administrator adds a new lens coating, brand, or doctor name, 
     the component calls `axios.post('/api/catalog', updatedData)`. This updates 
     the master catalog in MongoDB, immediately reflecting the new option in 
     all sales executive dropdowns across the store.

Q29: What is the primary difference between entryType 'New', 'Repeat', and 'Warranty'?
A29: 'New' represents a fresh customer prescription order; 'Repeat' denotes an 
     existing patient purchasing an additional pair with identical refraction; 
     'Warranty' tracks replacement lenses or frame repairs covered under warranty.

Q30: Why is request body parsing capped at 2MB in Express?
A30: Retail POS orders transfer small JSON payloads (< 20 kB). Setting 
     `express.json({ limit: '2mb' })` prevents malicious users from uploading 
     multi-megabyte JSON payloads that consume Node.js buffer memory and cause 
     out-of-memory denial of service.

Q31: How do you prevent multiple clicks from creating duplicate bills?
A31: On clicking "Save Bill", the UI enters an active processing state, and 
     subsequent clicks are ignored until the Axios request resolves or fails.

Q32: What trade-off was made regarding client-side role enforcement?
A32: Role switching (Admin vs Salesperson) is currently managed via client-side 
     PIN verification and React state. This is ideal for fast POS retail terminal 
     switching among employees, but in an enterprise cloud scenario, it should be 
     augmented with signed JWT HTTP-only cookies verified by Express middleware.

Q33: How does the search query in getBills support both text and numbers?
A33: In [billController.js], the sanitized query is checked. If it is numeric, 
     it checks both the raw number and the 3-digit padded version (e.g. '5' -> '005'), 
     while simultaneously matching patient name, phone, and MRD via case-insensitive regex.

Q34: How did you fix the missing icon crashes in React?
A34: Static code analysis with Oxlint detected multiple undeclared Lucide icons 
     (`Sparkles`, `Stethoscope`, `Phone`, `Eye`). These were missing imports that 
     would have caused fatal `ReferenceError` crashes during customer billing. 
     I resolved this by importing them explicitly from `lucide-react`.

20. TECHNICAL GLOSSARY

- ODM (Object Data Modeling): A library (like Mongoose) that maps JavaScript
